# AGENTS.md

## Product
Portfolio web app for booking sports pitches/courts (futsal, futebol 7, padel, ténis) in Portuguese clubs. One Next.js app with three areas on top of one ASP.NET Core API:
- **Jogador** (`/`): searches clubs, sees free slots, books and cancels.
- **Dono** (`/manage`): owns one or more clubs; manages pitches, opening hours, blocks, calendar, bookings for walk-in customers.
- **Admin** (`/admin`): platform owner. Created only by seed (env vars), never by an endpoint. Sees counts only, never player names/emails.

Source of truth: [docs/backlog.md](docs/backlog.md) (stories, acceptance criteria, rules) and [docs/stack.md](docs/stack.md) (architecture, stack, practices). Both are in Portuguese. Don't change stack, architecture or business rules without asking. Where they disagree, the Stack doc wins for technical choices (e.g. Next.js, not a plain React app).

## Architecture rules (detail in docs/stack.md)
- Backend: Clean Architecture in `backend/src/SportsBooking.{Domain,Application,Infrastructure,Api}`. Dependencies point inward only: Api → Infrastructure → Application → Domain.
- DI: built-in container, constructor injection only (no `IServiceProvider` in business code). Each layer registers itself: `services.AddApplication()`, `services.AddInfrastructure(config)`; `Program.cs` only composes. DbContext and its users are Scoped; a `BackgroundService` creates scopes via `IServiceScopeFactory`.
- Current time comes from injected `TimeProvider`, never `DateTime.UtcNow`/`Now`. Tests use `FakeTimeProvider`.
- Options pattern with `ValidateOnStart`.
- No generic repository (Application uses `IAppDbContext`), no MediatR, no AutoMapper, no FluentAssertions 8 (use Shouldly).
- Thin controllers. Entities have private setters and intention methods (`booking.Cancel(reason, now)`). Expected failures are returned results, not exceptions. `async` + `CancellationToken` all the way.
- Public IDs: `Guid.CreateVersion7()`. Money: `decimal` / `numeric(10,2)`. Dates: UTC `timestamptz`; opening hours as `TimeOnly` + club time zone `Europe/Lisbon`.
- Time (T04): convert local↔UTC only via `SportsBooking.Domain.Scheduling.ClubTime`. `Today()` gives the Lisbon date. Decided DST rules:
  - A local time that does not exist (clocks go forward, last Sunday of March) moves forward past the gap: 01:30 → 02:30 WEST.
  - A local time that happens twice (clocks go back, last Sunday of October) uses its first occurrence (WEST).
  - Slots come only from `SlotGenerator`: blocks of real elapsed time from opening, so DST days have one slot fewer/more and every slot lasts exactly its duration.
  - In the UI, times inside the repeated October hour are labelled "(verão)" / "(inverno)" via `formatLisbonSlotTime`; slots are never hidden.
- Opening hours: closing `00:00` = midnight. Hours past midnight (e.g. 22:00–02:00) are rejected; known MVP limitation.
- Frontend shows dates only through `frontend/src/lib/datetime.ts` (Lisbon, pt-PT); never `toLocaleString()` without `timeZone`.
- Overlapping bookings are prevented by a PostgreSQL exclusion constraint (`23P01` → 409), not only app code.
- Errors: ProblemDetails (RFC 9457) via `AddProblemDetails()` + global `IExceptionHandler`. Every error has a stable `code` (e.g. `slot_taken`) and `traceId`; the front end picks the message by `code`. Status codes: see table in docs/stack.md.
- Auth: ASP.NET Core Identity (core only). JWT access token (15 min) + rotating refresh token (7 days), both **httpOnly cookies**; front end learns the user via `GET /api/auth/me`. On a 401 the client calls `POST /api/auth/refresh` once and retries; login only if refresh fails. Refresh **must** reject deactivated accounts. Accepted trade-off: an already-issued access token stays valid up to 15 min after deactivation (no per-request active check). Front end and API are **same origin** (Next.js rewrites `/api/*` in dev, Caddy in prod); no CORS. API checks `Origin` on mutating requests.
- Accounts (US04): Identity core with `AppUser` (Infrastructure/Identity), snake_case tables (`users`, `roles`, `user_roles`, …) via `UseSnakeCaseNamingConvention()`, unique index on the normalized email. Profiles are the roles `Player`/`Owner`/`Admin` (`Domain.Accounts.Profiles`), seeded by migration. Password rule: `PasswordPolicy` (≥ 8 characters, no composition rules). Hashes: Identity v3 PBKDF2-HMAC-SHA512, 210,000 iterations (`PasswordHasherOptions`); older hashes are upgraded on the next successful check.
- Admin seed (US04): `AdminAccountSeeder` runs at startup in **every** environment, after migrations (production applies them before the API starts), from `AdminSeed:Email`/`AdminSeed:Password` (env `AdminSeed__*`, compose `ADMIN_SEED_*`, user-secrets locally). It is the **only** code allowed to assign the Admin profile (guarded by `AdminProfileGuardTests`). Decided rules:
  - Both settings absent → API starts, no admin, warning logged.
  - Only one set, malformed email or password < 8 characters → `AdminSeedOptionsValidator` fails `ValidateOnStart` and the API refuses to start, before touching the database. The error names the settings, never their values.
  - Surrounding whitespace on the email is trimmed before validating; everything else is strict (the password is used as is).
  - An existing admin is never modified (changing the password setting later has no effect); never a second admin, even with another email; an existing player/owner email is never promoted (warning logged, without the email). Never log the email or password.
  - Changing the admin password is manual (README, "Changing the admin password"): delete the admin row and restart with new settings.
- Sessions (US01): `ISessionService` (Application/Auth) implemented by `Infrastructure/Auth/SessionService`. Access token = HS256 JWT with only `sub` + `role` (`Jwt:Issuer`/`Audience` in appsettings, `Jwt:SigningKey` ≥ 32 bytes from env `Jwt__SigningKey`; Development has a local-only key). Refresh token (cookie `Path=/api/auth`, so refresh and logout both receive it) = 32 random bytes, stored only as SHA-256 in `refresh_tokens`; rotation is an atomic conditional update; a used token presented again revokes all sessions of the account; lifetime is absolute (rotation keeps the expiry). Deactivated = `users.deactivated_at` set (`AppUser.Deactivate(now)`). Cookies are written only by `Api/Auth/AuthCookies` (attributes from docs/stack.md); JwtBearer reads the `access_token` cookie.
- Authorization: fallback policy requires a session on every endpoint; public ones need `[AllowAnonymous]` (health, OpenAPI, register, login, refresh, logout). Side effect: anonymous requests to unknown routes get 401, not 404. Profile areas use `[Authorize(Policy = Profiles.Owner)]` (one policy per profile, named after it): another profile gets 403, no session 401. Per-owner checks are T02.
- Login/logout (US03): `POST /api/auth/login` → `LoginService` → `IAccountStore.AuthenticateAsync`; success = 200 with the `/me` body + both cookies. Every failure (unknown email, wrong password, locked out, deactivated) is the same 401 `invalid_credentials`, after the same PBKDF2 work (`FallbackPasswordHash`); only empty fields are 400. Identity lockout: `LoginLockout` (5 wrong passwords → 15 min). `POST /api/auth/logout` revokes the cookie's refresh token, clears both cookies, always 204 (works with an expired access token).
- Per-owner authorization (T02, `Application/Clubs/OwnedClubs`): the only way into clubs from the owner area. `ownedClubs.All()` is the signed-in owner's clubs (owner id from the session via `ICurrentUser`, never from the request); `ownedClubs.FindAsync(clubId)` returns the tracked club or `ClubErrors.NotFound` (404 `club_not_found`, identical for a missing club and another owner's club). Rules for every club resource (pitches, blocks, bookings, …): the controller lives under `api/manage/clubs/{clubId:guid}/…` with `[Authorize(Policy = Profiles.Owner)]`; the service resolves the club with `ownedClubs.FindAsync` (or filters from `ownedClubs.All()`, e.g. `dbContext.Pitches.Where(p => ownedClubs.All().Any(c => c.Id == p.ClubId))`) **before** validating the request; it never reads `IAppDbContext.Clubs` (or a child table) by id directly. `OwnerAreaAccessTests` discovers every `/api/manage` route and checks 401/403 and the cross-owner 404, so name the club route parameter `clubId` and give POST/PUT bodies that pass validation for its `ValidBody` (extend it if a new endpoint needs other fields).
- Rate limiting (US03, `Api/Security/RateLimitingSetup`): built-in fixed window per client IP (IPv6 per /64, `ClientPartition`) on login, register and refresh, `[EnableRateLimiting(AuthRateLimits.*)]`, limits in `RateLimiting:Auth`; 429 `too_many_requests` + `Retry-After`. The client IP comes from `X-Forwarded-For` only if the connection is a proxy in `ForwardedHeaders:KnownProxies`/`KnownNetworks` (none by default; production: Caddy only, see README). Never trust the Next.js container: its rewrite passes on a browser-sent `X-Forwarded-For`.
- Origin check (`Api/Security`): POST/PUT/PATCH/DELETE need an `Origin` equal to one of `Security:AllowedOrigins` (Development: :3000 and :5080; production via `Security__AllowedOrigins__0`), else 403 `origin_not_allowed`. A missing `Origin` is rejected too (decided). Server-side callers that mutate (Route Handlers, Server Actions; the server never refreshes sessions) must send the site's `Origin` header; Server Component GETs are unaffected. Today every mutating call is a browser `fetch` to a relative URL, and browsers send `Origin` on those themselves.
- Pitches (US07, `Application/Pitches/PitchService`, controller `api/manage/clubs/{clubId}/pitches`): the first club resource, so it shows the T02 rules in use. The service first checks the club with `ownedClubs.All()` (404 `club_not_found`, before validating), then reads pitches only through `OwnedPitches(clubId)` (filtered by the club and by `ownedClubs.All()`); a pitch that is not in that club is 404 `pitch_not_found`. Sport = stable codes `futsal`/`football7`/`padel`/`tennis` (`Domain/Pitches/Sports`, stored as text with a check constraint); status `active`/`inactive` (never deleted; `POST …/deactivate` and `…/reactivate` are idempotent). Names are unique per club ignoring case through `pitches.name_key` (trimmed, upper-case invariant) and a unique index; the loser of a race gets the same 400 on `name` via `IPitchStore.TrySaveAsync`. Price: `numeric(10,2)`, > 0 and ≤ 500. Deactivating takes `IPitchLock` and is refused while confirmed bookings have not ended (422 `pitch_has_future_bookings`, `count`). Pitch lookups go through `Application/Pitches/OwnedPitches` (`FindAsync(clubId, pitchId)`: club first, then the pitch inside that club); use it for every pitch resource.
- Pitch schedule (US08, `PitchScheduleService`, controller `api/manage/clubs/{clubId}/pitches/{pitchId}/schedule` and `/slots`): `Pitch.SlotDurationMinutes` (30/60/90, a new pitch has 60) and `Pitch.OpeningDays` (owned rows in `pitch_opening_hours`, one per open weekday, local `time` values; a weekday with no row is closed, so a new pitch is closed every day). `Pitch.ChangeSchedule` replaces the whole week in place; `Pitch.SlotsOn(date, timeZone)` is the only way to get a pitch's slots and calls `SlotGenerator` (never write another generator). Times go in 30-minute steps (`PitchScheduleRules.TimeStepMinutes`). The booking window is `Domain/Scheduling/BookingWindow` (today..today+30 in the club's time zone, today from `ClubTime.Today(timeProvider, …)`). Frontend: the "Horário" button on a pitch row (`PitchSection`) opens `ScheduleEditor` (RHF + Zod, seven rows, `type=time` in 30-minute steps, `Fechado` checkbox; API keys `monday.closes` map to form paths `days.monday.closes` and a whole-day message to that day's toggle) and `SlotPreview` (date picker limited to `previewDateRange()`: Lisbon today..+30; times only through `formatLisbonSlotTime`). Date arithmetic on `YYYY-MM-DD` keys lives in `lib/datetime.ts` (`addDaysToDateKey`, `isDateKey`). Integration tests on a fake clock: `factory.WithWebHostBuilder(... ConfigureTestServices(... AddSingleton<TimeProvider>(new FakeTimeProvider(...))))`, but take sessions from the shared `factory`: access-token expiry is checked against the system clock.
- Blocks (US09, `BlockService`, controller `…/pitches/{pitchId}/blocks`): `Block` = pitch + UTC `[StartsAt, EndsAt)` + optional reason (≤ 200); input is Lisbon local `yyyy-MM-ddTHH:mm` (30-minute steps), converted with `ClubTime.ToUtc` (`BlockCheck`), start not in the past, end ≤ now + 90 days. Creating runs `IPitchLock.LockAsync(pitchId)` (Infrastructure `PitchLock`: transaction + `SELECT … FOR UPDATE` on the pitch row), then checks overlaps, saves and commits, all on the same `IAppDbContext`. Under the same lock, after the block check, confirmed bookings that overlap refuse the block (409 `block_overlaps_bookings`, ProblemDetails extension `bookings` with ids and UTC times); booking creation takes the same `IPitchLock` before checking blocks (docs/stack.md). Overlap is half-open, touching is fine; overlap = 409 `block_overlap`, deleting a started block = 422 `block_already_started` (`ErrorKind.Unprocessable`), unknown block = 404 `block_not_found`. The slot preview marks `blocked` slots (any overlap); free-slot logic for players (US17) must use the same overlap rule. Frontend: the "Bloqueios" button on a pitch row (`PitchSection`, one panel at a time with "Horário") opens `BlocksSection` (list, removal with an inline confirmation, `BlockForm` with date + time fields per end; API `start`/`end` errors go on the date field of that end, `block_overlap` shows above the buttons) and the preview shows `Bloqueado`. Block and preview queries live under `["pitches", clubId, pitchId, ...]`, so changing a block invalidates the preview.
- Bookings (T03, US18, `Application/Bookings/BookingService`, controller `api/bookings`, Player policy): `Booking` = pitch + player (nullable `player_id` guarded by `ck_bookings_has_player` until US13 adds customer bookings) + UTC `[StartsAt, EndsAt)` + price copied from the pitch + `Status` stored as the enum name (`HasConversion<string>()`), API codes `confirmed`/`cancelled_by_player`/`cancelled_by_club`/`no_show`. The request is `{ pitchId, startsAt }` with `startsAt` an instant with its zone; `Pitch.SlotStartingAt(startUtc, timeZone)` (generated slots of the start's Lisbon date) gives the end. Order: validation (400) → pitch (404) → owner active (`IAccountStore.IsActiveAsync`, 422 `club_unavailable`) → `IPitchLock` → re-read the pitch → inactive (422) → window on the Lisbon date (422 `outside_booking_window`) → slot match (422 `invalid_slot`) → started (422 `slot_started`) → blocks (409 `slot_blocked`) → insert through `IBookingStore.TryAddAsync`. Overlap with another booking is left to the exclusion constraint `bookings_no_overlap` (raw SQL in the `AddBookings` migration, needs `btree_gist`), whose 23P01 the store turns into 409 `slot_taken`; never add an app-level shortcut that bypasses it. `ServiceError.Extensions` carries extra ProblemDetails members (`count`, `bookings`). The owner slot preview also marks `booked` slots (confirmed bookings only). **My bookings and cancelling (US19):** `MyBookingsService` (`GET /api/me/bookings?scope=upcoming|past&page=`, `GET /api/bookings/{id}`, both Player-only and filtered by the session's player, so another player's booking is the same 404 `booking_not_found`) and `BookingCancellationService` (`POST /api/bookings/{id}/cancel`). The rules live in the entity: `Booking.CancelByPlayer(window, now)` returns a `CancellationOutcome` (`Cancelled`, `NotConfirmed`, `OutsideWindow`) and changes the status only for `Cancelled`; the deadline is `StartsAt - window`, cancelling needs `now` strictly before it, and the window is the club's **current** `CancellationWindowHours`, passed in, never stored in the booking. Order of refusals: 404 → 422 `booking_not_confirmed` → 422 `outside_cancellation_window` (extension `cancellationDeadline`, a UTC instant). Cancelling runs under `IPitchLock` and re-reads the booking inside it: that is what makes two concurrent cancels one 200 and one 422 (the test of 12 fails without the lock); bookings are never deleted, and the exclusion constraint only covers `Confirmed`, so a cancelled slot is free again. POST `/api/bookings` answers 201 with `Location: /api/bookings/{id}`. The cancellation email is US22. When a query is projected into a private row type and then filtered or ordered (`Where(row => row.Status…)`), build the row with an object initializer, not a constructor call: EF cannot translate member access through `new Row(…)`.
- Public catalog (US16, US17, `Application/Catalog`, controllers `ClubsController` and `LocalitiesController`, all `[AllowAnonymous]` and read-only): the counterpart of the owner rules. `VisibleClubs.All()` is the only way into clubs from the public pages (never read `IAppDbContext.Clubs` there): a club is visible when its owner is not deactivated (`IAppDbContext.ActiveAccountIds`, US29) and it has an active pitch; an unknown, empty or hidden club is the same 404 `club_not_found`, and a pitch that is unknown, inactive or from another club is 404 `pitch_not_found`, both checked before the date. Responses carry nothing about players or owners (no names, emails, account ids, booking or block ids, block reasons, or the club's own id) and a slot has one `available` flag, never a reason; every public endpoint has a test that scans its body for such data, so extend it when a field is added. Endpoints: `GET /api/clubs?sport=&locality=&date=&page=` (20 per page, ordered by name ignoring case, `hasFreeSlots` worked out only for the page's clubs), `GET /api/localities`, `GET /api/clubs/{slug}`, `GET /api/clubs/{slug}/pitches/{pitchId}/slots?date=`. Locality search = equality on `clubs.locality_key` (`ClubRules.LocalityKey`: no accents, lower case, single spaces; kept in step by `Club`, indexed). **One slot calculation:** `PitchDayCalendar` turns generated slots into `DaySlot`s (blocked/booked, reading blocks and confirmed bookings of many pitches with one query each) and `DaySlot.IsFreeAt(now)` is the only definition of "free" (nothing overlaps, even partly, and it has not started; starting now counts as started via `TimeSlot.HasStartedBy`); the owner preview, the player's slots and the search all use them, so never write another. `BookingDateInput.Parse` gives all three the same date checks (today..today+30 in Lisbon, `yyyy-MM-dd`, 400 on `date`). Query-string numbers that a client can get wrong are read as text and judged by our own validation, so the error is pt-PT and not MVC's English binding message (see the search's `page`).
- Logging of database failures (T03): a lost booking race is expected, so it must never be an Error. `BookingStore` logs it at Information with the pitch and slot only, never the player; EF's `SaveChangesFailed` and `CommandError` events are lowered to Debug in `AddInfrastructure` (`ConfigureWarnings`, not a category filter) and `FailedCommandLogger` (a `DbCommandInterceptor`, same category and command text as EF's) logs every failed command at Error again **except** the `bookings_no_overlap` exclusion violation, so no other failure goes quiet. An error nobody handles reaches `GlobalExceptionHandler`, which logs it at Error and answers 500 (`BookingLoggingTests`, with the test-only `DatabaseFailureTestController`). Expected conflicts of other kinds (unique pitch name, slug, email) still log as errors.
- Application data access: `IAppDbContext` (Application/Common, implemented by `AppDbContext`): services use its `DbSet`s with EF Core directly (projections with `AsNoTracking`, lists paginated with `PageRequest`/`PagedResponse<T>` and a defined order). Database-specific behaviour (e.g. unique-index retries) sits behind a small store interface implemented in Infrastructure (`IClubStore`, like `IAccountStore`).
- Expected failures: services return `Result<T>` / `ServiceError` (`Application/Common/Result.cs`); controllers turn them into ProblemDetails with `this.Problem(error)` (`Api/ErrorHandling/ServiceErrorResults`). Validation = FluentValidation in the service, field keys camelCase (`ToFieldErrors()`), 400 `validation_failed`. Request DTO properties stay non-nullable; MVC's implicit `[Required]` is off so missing fields get the pt-PT FluentValidation messages. `ProblemDetailsSchemaTransformer` documents `code`/`traceId` in OpenAPI.
- Registration (US01, US02): `POST /api/auth/register` (player) and `POST /api/auth/register/owner` (owner) → `AccountRegistrationService.RegisterPlayerAsync`/`RegisterOwnerAsync` → `IAccountStore.CreateAsync(account, profile)` (Identity; account + its profile in one transaction; the unique email index settles races). Taken email = 409 `email_taken` with one fixed message for any profile (US01 requires saying it; see the trade-off in docs/backlog.md). Shared rules in `Domain/Accounts` (`EmailAddressPolicy`, `AccountNamePolicy`, `PhoneNumberPolicy`, `PasswordPolicy`), also used by the admin seed.
- Frontend auth (US03): the server never refreshes a session (the `refresh_token` cookie is `Path=/api/auth`, so page requests do not carry it); no token renewal in `proxy.ts`: `src/proxy.ts` (matcher `/manage/*`, `/admin/*`) only sets the `x-pathname` request header (path + query, always overwriting a client-sent value) so `AreaGuard` can redirect to `/login?next=<full path>`; `areaDecision` runs it through `safeNext`, so a path outside the area falls back to the area home. Area guards live in the `/manage` (Owner) and `/admin` (Admin) layouts: `AreaGuard` (inside `<Suspense>`, required by `cacheComponents` for cookie reads) calls `lib/server/session.ts` (`server-only`; `GET /api/auth/me` on `API_INTERNAL_URL` with the user's `Cookie`, `no-store`; `docker-compose.yml` defines it once and passes it as build arg (rewrites) and as the frontend container's environment; the Dockerfile has no default). Redirect decisions are pure functions in `lib/auth/redirects.ts` (`areaDecision`, `safeNext`, `profileHome`, `loginUrl`). No session → `/login?next=<area home>`; another profile → its own area. `/login` first tries a silent browser `POST /api/auth/refresh` (`trySilentRefresh`), then shows the form; `next` is used only if it is a relative path with a single leading `/` inside the user's area, else the profile's home (Player `/`, Owner `/manage`, Admin `/admin`). Public pages stay public. `/login`, `/register` and `/register/owner` wrap their content in `GuestOnly` (server-side: a signed-in user goes to `profileHome`). `/manage` lists the owner's clubs (`ClubList`, TanStack Query) with `NoClubsYet` as the empty state; `/manage/clubs/new` and `/manage/clubs/{id}` hold `ClubForm`; a 404 from the API (missing or another owner's club) renders the same `ClubNotFound` page, and a malformed id is `notFound()` on the server. Below the club form, `/manage/clubs/{id}` shows `PitchSection` (`features/pitches`, TanStack Query keys `["pitches", clubId, "list", page]`): list with add, edit, deactivate, reactivate; `PitchForm` takes the price as typed text (`features/pitches/price.ts` reads "12,50" or "12.50", shows "12,50 €" via `Intl` pt-PT) and sends a number; sports are the API codes with pt-PT labels in `features/pitches/sports.ts`. The logout button (`Sair`) clears the TanStack Query cache and goes to `/login`. Across tabs, `client.ts` takes the Web Lock `sportsbooking-refresh` so one tab refreshes at a time, repeating the original request first (no `navigator.locks` = per-tab sharing only).
- Public pages (US16, US17, US18; `features/catalog` reads, `features/booking` books): `/` is `ClubSearch` (client; the search lives in the URL `?sport=&locality=&date=&page=`, read by `filtersFromParams` and written with `router.replace`; TanStack Query keys under `["catalog", …]`, see `features/catalog/api.ts`). `/clubs/{slug}` is a Server Component: `loadPublicClub` (`lib/server/public-club.ts`, `server-only`, `API_INTERNAL_URL` via `lib/server/api-url.ts`, `no-store`, **no cookies**) returns the club or calls `notFound()` (also for a slug that `isClubSlug` says cannot exist, without asking the API); it renders `ClubDetails` and the client `ClubBooking` inside `<Suspense>` (it reads the URL). The booking choice is **in the URL, not in Zustand**: `?pitch=&date=&slot=<instant with its zone>` (`features/booking/selection.ts`), because that is what lets a visitor who clicks "Entrar para reservar" (`/login?next=<this address>`) come back to the same pitch, date and slot; `safeNext` already accepts any public path for a Player and sends an Owner or Admin to their own area, so it needed no change. The same `next` goes through sign-up: the login screen's "Criar conta" link is `registerUrl(next)`, `RegisterScreen` (client, reads `?next=`) gives it to the player `RegisterForm`, which ends with `safeNext(next, profile)` (an unsafe value is dropped; owner sign-up never uses it). Only a Player gets "Confirmar reserva"; Owner and Admin see the slots read-only (`SlotList interactive={false}`) and a note; a visitor gets the sign-in link. A refused booking shows the message by code (`publicErrorMessage`: `club_not_found` is worded for visitors, the shared text says "não é teu"), clears the slot from the URL and reloads the club's slots (`clubSlotsQueryKey`); 401 goes back to login; success refreshes `["catalog"]`. An unavailable slot is `disabled` and never says why. The booking request carries only `pitchId` and `startsAt` (the zoned instant exactly as the slot list gave it).
- Frontend: Next.js App Router, TypeScript strict, Tailwind + shadcn/ui. Server Components by default; `'use client'` as low as possible. Server code that reads cookies or the internal API URL imports `server-only`. API types generated from OpenAPI (openapi-typescript), never hand-written.
- State: **TanStack Query** for anything from the API (invalidate after mutations, refetch slots on 409). **Zustand** only for shared UI state (booking step, calendar view); never copy API data or tokens/personal data into it or `localStorage`.
- Forms: React Hook Form + Zod (UX only; the API always re-validates with FluentValidation). Map API `errors` to fields with `setError`. Zod schemas mirror the API's limits and pt-PT messages (e.g. `features/auth/schemas/register.ts`). Use `noValidate` so browser validation does not replace ours. Pages stay mounted across navigations (`cacheComponents`), so reset forms with secrets after submit.
- Frontend API access: only via `src/lib/api/client.ts` (`apiRequest`/`apiJson`): same-origin `/api/*`, ProblemDetails → `ApiError` (`status`, `code`, `fieldErrors`, `traceId`), one shared refresh on 401 then one retry. Messages by code in `src/lib/api/error-messages.ts`; unexpected mutation errors go to a toast (sonner). Current user: `useCurrentUser()` (`features/auth`), query key `["auth", "me"]`.
- Integration tests run against real PostgreSQL (Testcontainers), never the EF in-memory provider.

## Business rules (decided)
- One email = one account = one profile.
- An owner may have several clubs; a club has exactly one owner.
- Cancellation window per club, default 24 h; the window in force at cancellation time applies.
- Bookings from today up to 30 days ahead. Slot length per pitch: 30, 60 or 90 min.
- Bookings are never deleted; they change status: Confirmed, CancelledByPlayer, CancelledByClub, NoShow (UI shows pt-PT labels).
- Each booking stores the price at booking time. No payments in the MVP.
- Dates stored in UTC, shown in Lisbon time regardless of the browser time zone.
- One marketplace: a player account works at every club of every owner; no per-owner sites or domains. URLs: public club page `/clubs/{slug}` (unique slug from the name at creation, unchanged on rename); owner area `/manage/clubs/{id}` (public GUID).
- Another owner's resources return 404 (don't reveal existence); wrong profile returns 403.

## Conventions
- Code, identifiers, commits, branch names: **English**. User-facing UI text and API error messages: **Portuguese (pt-PT)**.
- Commits: Conventional Commits with the story ID: `feat(US18): ...`, `test(T03): ...`, `fix(US19): ...`.
- Branches: `feat/US18-short-name` (`chore/T01-...` for technical stories). `main` is protected; merge via PR with green CI (squash).
- Merge order: branch from `main`, one PR per story, squash merge.
- Each bug gets a reproducing test first, then the fix.

## Gotchas
- Next.js 16.4 differs from older versions (e.g. `error.tsx` gets `retry`, `cacheComponents` is on, `proxy.ts` replaces `middleware.ts`). Read [frontend/AGENTS.md](frontend/AGENTS.md) and the bundled docs in `frontend/node_modules/next/dist/docs/` before writing frontend code.
- Build-time OpenAPI generation starts the app as `GetDocument.Insider`; `Program.cs` gives it placeholder settings and skips migrations. Keep startup code safe for that.
- Integration tests: the shared `ApiFactory` host applies migrations on startup (`Database:ApplyMigrationsOnStartup=true`, as Development does). For startup behaviour (seeding), use `factory.CreateIsolatedApp(databaseName, settings)`: own database, captured logs via `GetFakeLogCollector()`.
- Integration test data: `TestVenues` (extension methods on the app factory) builds owners, clubs, pitches (with opening hours), blocks, bookings, price and schedule changes and deactivations straight through the domain model, with unique names and slugs; use it instead of going through the owner API when a test only needs data to read back. The whole assembly shares one database, so give each test its own locality or club names when it lists things. For a fixed clock and captured logs: `factory.WithWebHostBuilder(b => { b.ConfigureTestServices(s => s.AddSingleton<TimeProvider>(new FakeTimeProvider(...))); b.ConfigureLogging(l => l.AddFakeLogging()); })`; starting the host runs its own database commands, so read `app.Services` before taking a "before" count. The whole suite needs Docker running (Testcontainers): without it every integration test fails to connect, which looks like hundreds of failures.
- Integration test clients: the site origin is `https://localhost` (`ApiFactory.SiteOrigin`; HTTPS so Secure cookies work). `factory.CreateBrowserClient()` = cookie jar + `Origin`; `factory.CreateSiteClient()` = `Origin`, no jar (send cookies with `request.WithCookies(...)`, read them with `response.SetCookies()`); `factory.CreateSignedInPlayerAsync()` / `CreateSignedInAsync(profile)` give an account and session tokens without slow password hashing; `CreateAccountAsync(profile, password)` makes an account of any profile that can log in (owners have no sign-up until US02).
- The test host (and only it) adds `TestClientAddress` (header `X-Test-Connection-Address` sets the connection IP; `request.From("203.0.113.10")`) and `ProfileAreasTestController` (`/test-only/areas/{player|owner|admin}`). It sets very high rate limits because every test request shares one address; rate limiting is tested on isolated apps (`RateLimitingTests`).
- Build-time OpenAPI generation also runs `ValidateOnStart`: every new required setting needs a placeholder in the `isOpenApiGeneration` block of `Program.cs`.
- Frontend component tests: MSW (`src/test/msw.ts`) is global and fails on unhandled requests; add handlers with `server.use(...)`. Render with `renderWithProviders` (`src/test/render.tsx`) and mock `next/navigation` where a component uses the router. For components driven by the URL (`useSearchParams`, `router.replace`), mock `next/navigation` with `vi.mock("next/navigation", async () => import("@/test/navigation"))`: its URL is real (`resetNavigation("/path?query")`, `currentPath()`), so a `router.replace` re-renders the component as in the app; it also exports a `notFound` that throws `NotFoundSignal`.
- `dotnet ef migrations remove` needs a running database; to drop an unapplied migration, delete its two files and restore `AppDbContextModelSnapshot.cs` from git.
- EF migrations folder is marked `generated_code` (its own `.editorconfig`); test projects allow underscores in test names (CA1707 off).
