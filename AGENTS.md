# AGENTS.md

## Product
Portfolio web app (the UI is available in Portuguese (pt-PT, default) and English) for booking sports pitches/courts (futsal, 7-a-side football, padel, tennis; in the UI: `futsal`, `futebol 7`, `padel`, `ténis`) in Portuguese clubs. One Next.js app with three areas on top of one ASP.NET Core API:
- **Jogador** (`/`): searches clubs, sees free slots, books and cancels.
- **Dono** (`/manage`): owns one or more clubs; manages pitches, opening hours, blocks, calendar, bookings for walk-in customers.
- **Admin** (`/admin`): platform owner. Created only by seed (env vars), never by an endpoint. Sees counts only, never player names/emails.

Source of truth: [docs/backlog.md](docs/backlog.md) (stories, acceptance criteria, rules) and [docs/stack.md](docs/stack.md) (architecture, stack, practices). Both are in English. Don't change stack, architecture or business rules without asking. Where they disagree, the Stack doc wins for technical choices (e.g. Next.js, not a plain React app).

## Architecture rules (detail in docs/stack.md)
- Backend: Clean Architecture in `backend/src/SportsBooking.{Domain,Application,Infrastructure,Api}`. Dependencies point inward only: Api → Infrastructure → Application → Domain.
- DI: built-in container, constructor injection only (no `IServiceProvider` in business code). Each layer registers itself: `services.AddApplication()`, `services.AddInfrastructure(config)`; `Program.cs` only composes. DbContext and its users are Scoped; a `BackgroundService` creates scopes via `IServiceScopeFactory`.
- Current time comes from injected `TimeProvider`, never `DateTime.UtcNow`/`Now`. Tests use `FakeTimeProvider`.
- Options pattern with `ValidateOnStart`.
- No generic repository (Application uses `IAppDbContext`), no MediatR, no AutoMapper, no FluentAssertions 8 (use Shouldly).
- Thin controllers. Entities have private setters and intention methods (`booking.Cancel(reason, now)`). Expected failures are returned results, not exceptions. `async` + `CancellationToken` all the way.
- Public IDs: `Guid.CreateVersion7()`. Money: `decimal` / `numeric(10,2)`. Dates: UTC `timestamptz`; opening hours as `TimeOnly` + club time zone `Europe/Lisbon`.
- Time (T04): convert local↔UTC only via `SportsBooking.Domain.Scheduling.ClubTime`. `Today()` gives the Lisbon date. Decided DST rules:
  - A local time that does not exist (clocks go forward, last Sunday of March) moves forward past the gap: 01:30 → 02:30 WEST.
  - A local time that happens twice (clocks go back, last Sunday of October) uses its first occurrence (WEST).
  - Slots come only from `SlotGenerator`: blocks of real elapsed time from opening, so DST days have one slot fewer/more and every slot lasts exactly its duration.
  - In the UI, times inside the repeated October hour are labelled `(verão)` ("summer") / `(inverno)` ("winter") via `formatLisbonSlotTime` (through `useFormats().slotTime`; the words are in the catalogs, `(summer time)`/`(winter time)` in English); slots are never hidden.
- Opening hours: closing `00:00` = midnight. Hours past midnight (e.g. 22:00–02:00) are rejected; known MVP limitation.
- Frontend shows dates only through `frontend/src/lib/datetime.ts` (Lisbon, `pt-PT` or `en-GB`), from components through `useFormats()` (`src/i18n/formats.ts`); never `toLocaleString()` without `timeZone`.
- Overlapping bookings are prevented by a PostgreSQL exclusion constraint (`23P01` → 409), not only app code.
- Errors: ProblemDetails (RFC 9457) via `AddProblemDetails()` + global `IExceptionHandler`. Every error has a stable `code` (e.g. `slot_taken`) and `traceId`; the front end picks the message by `code`. Status codes: see table in docs/stack.md.
- Auth: ASP.NET Core Identity (core only). JWT access token (15 min) + rotating refresh token (7 days), both **httpOnly cookies**; front end learns the user via `GET /api/auth/me`. On a 401 the client calls `POST /api/auth/refresh` once and retries; login only if refresh fails. Refresh **must** reject deactivated accounts. Accepted trade-off: an already-issued access token stays valid up to 15 min after deactivation (no per-request active check; a **deleted** account is the exception, US30). Front end and API are **same origin** (Next.js rewrites `/api/*`, in development and in production on Vercel, T06); no CORS. API checks `Origin` on mutating requests.
- Accounts (US04): Identity core with `AppUser` (Infrastructure/Identity), snake_case tables (`users`, `roles`, `user_roles`, …) via `UseSnakeCaseNamingConvention()`, unique index on the normalized email. Profiles are the roles `Player`/`Owner`/`Admin` (`Domain.Accounts.Profiles`), seeded by migration. Password rule: `PasswordPolicy` (≥ 8 characters, no composition rules). Hashes: Identity v3 PBKDF2-HMAC-SHA512, 210,000 iterations (`PasswordHasherOptions`); older hashes are upgraded on the next successful check.
- Admin seed (US04): `AdminAccountSeeder` runs at startup in **every** environment, after migrations (production applies them before the API starts), from `AdminSeed:Email`/`AdminSeed:Password` (env `AdminSeed__*`, compose `ADMIN_SEED_*`, user-secrets locally). It is the **only** code allowed to assign the Admin profile (guarded by `AdminProfileGuardTests`). Decided rules:
  - Both settings absent → API starts, no admin, warning logged.
  - Only one set, malformed email or password < 8 characters → `AdminSeedOptionsValidator` fails `ValidateOnStart` and the API refuses to start, before touching the database. The error names the settings, never their values.
  - Surrounding whitespace on the email is trimmed before validating; everything else is strict (the password is used as is).
  - An existing admin is never modified (changing the password setting later has no effect); never a second admin, even with another email; an existing player/owner email is never promoted (warning logged, without the email). Never log the email or password.
  - Changing the admin password is the `set-admin-password` command (README, "Changing the admin password"; `Infrastructure/Identity/AdminPasswordCommand`): `Program.cs` runs it after migrations and the admin seed when the first argument is `set-admin-password`, and exits without starting the host. The new password comes only from the `ADMIN_NEW_PASSWORD` environment variable (any extra argument is refused, never echoed), is checked with `PasswordPolicy`, replaces the admin's hash in one transaction with the revocation of all the admin's refresh tokens (and clears a lockout), and neither it nor the email is ever printed or logged. It never assigns the Admin profile, so `AdminProfileGuardTests` still holds.
- Sessions (US01): `ISessionService` (Application/Auth) implemented by `Infrastructure/Auth/SessionService`. Access token = HS256 JWT with only `sub` + `role` (`Jwt:Issuer`/`Audience` in appsettings, `Jwt:SigningKey` ≥ 32 bytes from env `Jwt__SigningKey`; Development has a local-only key). Refresh token (cookie `Path=/api/auth`, so refresh and logout both receive it) = 32 random bytes, stored only as SHA-256 in `refresh_tokens`; rotation is an atomic conditional update; a used token presented again revokes all sessions of the account; lifetime is absolute (rotation keeps the expiry). Deactivated = `users.deactivated_at` set; in production only by the conditional `UPDATE` in `OwnerStatusStore.TryChangeAsync` (US29) and by the account deletion (US30), while `AppUser.Deactivate(now)` is used only by tests. Cookies are written only by `Api/Auth/AuthCookies` (attributes from docs/stack.md); JwtBearer reads the `access_token` cookie.
- Authorization: fallback policy requires a session on every endpoint; public ones need `[AllowAnonymous]` (health, OpenAPI, register, login, refresh, logout). Side effect: anonymous requests to unknown routes get 401, not 404. Profile areas use `[Authorize(Policy = Profiles.Owner)]` (one policy per profile, named after it): another profile gets 403, no session 401. Per-owner checks are T02.
- Login/logout (US03): `POST /api/auth/login` → `LoginService` → `IAccountStore.AuthenticateAsync`; success = 200 with the `/me` body + both cookies. Every failure (unknown email, wrong password, locked out, deactivated) is the same 401 `invalid_credentials`, after the same PBKDF2 work (`FallbackPasswordHash`); only empty fields are 400. Identity lockout: `LoginLockout` (5 wrong passwords → 15 min). `POST /api/auth/logout` revokes the cookie's refresh token, clears both cookies, always 204 (works with an expired access token).
- Per-owner authorization (T02, `Application/Clubs/OwnedClubs`): the only way into clubs from the owner area. `ownedClubs.All()` is the signed-in owner's clubs (owner id from the session via `ICurrentUser`, never from the request); `ownedClubs.FindAsync(clubId)` returns the tracked club or `ClubErrors.NotFound` (404 `club_not_found`, identical for a missing club and another owner's club). Rules for every club resource (pitches, blocks, bookings, …): the controller lives under `api/manage/clubs/{clubId:guid}/…` with `[Authorize(Policy = Profiles.Owner)]`; the service resolves the club with `ownedClubs.FindAsync` (or filters from `ownedClubs.All()`, e.g. `dbContext.Pitches.Where(p => ownedClubs.All().Any(c => c.Id == p.ClubId))`) **before** validating the request; it never reads `IAppDbContext.Clubs` (or a child table) by id directly. `OwnerAreaAccessTests` discovers every `/api/manage` route and checks 401/403 and the cross-owner 404, so name the club route parameter `clubId` and give POST/PUT bodies that pass validation for its `ValidBody` (extend it if a new endpoint needs other fields).
- Rate limiting (US03, `Api/Security/RateLimitingSetup`): built-in fixed window per client IP (IPv6 per /64, `ClientPartition`) on login, register, refresh and the two password-reset steps, `[EnableRateLimiting(AuthRateLimits.*)]`, limits in `RateLimiting:Auth`, and (T06) on the public read endpoints (`ClubsController`, `LocalitiesController`: `[EnableRateLimiting(PublicRateLimits.Read)]`, one limit shared by search, localities, club page and slots, `RateLimiting:Public` = 120 per minute, provisional); 429 `too_many_requests` + `Retry-After`. The client IP comes from `X-Forwarded-For` only if a proxy is trusted: `ForwardedHeaders:KnownProxies`/`KnownNetworks`, or `ForwardedHeaders:TrustAnyProxy` (production on Render, whose proxies have no listable addresses, provisional). None by default, and then the headers are switched off (the middleware believes anyone when both lists are empty). `ForwardedHeaders:ForwardLimit` (1) is how many entries are read, from the right. On Render the API is public, so the header can be forged by a direct caller: IP limits are best-effort and the Identity lockout is the real protection against guessing passwords. A 429 logs the resulting client partition, which is also how the first deploy finds the right limit (docs/deployment/environment-variables.md). In docker compose never trust the Next.js container: its rewrite passes on a browser-sent `X-Forwarded-For`.
- Origin check (`Api/Security`): POST/PUT/PATCH/DELETE need an `Origin` equal to one of `Security:AllowedOrigins` (Development: :3000 and :5080; production via `Security__AllowedOrigins__0`), else 403 `origin_not_allowed`. A missing `Origin` is rejected too (decided). Server-side callers that mutate (Route Handlers, Server Actions; the server never refreshes sessions) must send the site's `Origin` header; Server Component GETs are unaffected. Today every mutating call is a browser `fetch` to a relative URL, and browsers send `Origin` on those themselves.
- Security headers (T06): the site's come from `frontend/next.config.ts` through `src/lib/security-headers.ts` (CSP, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`); the `/reset-password` rule is listed after the general one and overrides `Referrer-Policy` and `Cache-Control`. HSTS and `upgrade-insecure-requests` only when the **build** has `ENABLE_HSTS=true` (a `frontend/Dockerfile` build argument, off by default, never in development; the headers are written at build time). Known relaxation, marked provisional in the backlog: `script-src` and `style-src` allow `'unsafe-inline'`, because Next.js streams inline data scripts and `cacheComponents` rules out a nonce; a strict policy means giving up `cacheComponents`, an architecture decision. Load nothing from another origin without changing the policy and its test (`security-headers.test.ts`). Zod runs with `jitless` (`lib/zod-config.ts`, imported by `Providers`) so it does not probe `eval` under the policy. The API adds `X-Content-Type-Options: nosniff` to every response (`UseResponseSecurityHeaders`, `Api/Security/SecuritySetup.cs`) and Kestrel sends no `Server` header (`ResponseHeadersTests`). Dependabot (`.github/dependabot.yml`) proposes weekly grouped minor and patch updates; majors are reviewed by hand.
- Pitches (US07, `Application/Pitches/PitchService`, controller `api/manage/clubs/{clubId}/pitches`): the first club resource, so it shows the T02 rules in use. The service first checks the club with `ownedClubs.All()` (404 `club_not_found`, before validating), then reads pitches only through `OwnedPitches(clubId)` (filtered by the club and by `ownedClubs.All()`); a pitch that is not in that club is 404 `pitch_not_found`. Sport = stable codes `futsal`/`football7`/`padel`/`tennis` (`Domain/Pitches/Sports`, stored as text with a check constraint); status `active`/`inactive` (never deleted; `POST …/deactivate` and `…/reactivate` are idempotent). Names are unique per club ignoring case through `pitches.name_key` (trimmed, upper-case invariant) and a unique index; the loser of a race gets the same 400 on `name` via `IPitchStore.TrySaveAsync`. Price: `numeric(10,2)`, > 0 and ≤ 500. Deactivating takes `IPitchLock` and is refused while confirmed bookings have not ended (422 `pitch_has_future_bookings`, `count`). Pitch lookups go through `Application/Pitches/OwnedPitches` (`FindAsync(clubId, pitchId)`: club first, then the pitch inside that club); use it for every pitch resource.
- Pitch schedule (US08, `PitchScheduleService`, controller `api/manage/clubs/{clubId}/pitches/{pitchId}/schedule` and `/slots`): `Pitch.SlotDurationMinutes` (30/60/90, a new pitch has 60) and `Pitch.OpeningDays` (owned rows in `pitch_opening_hours`, one per open weekday, local `time` values; a weekday with no row is closed, so a new pitch is closed every day). `Pitch.ChangeSchedule` replaces the whole week in place; `Pitch.SlotsOn(date, timeZone)` is the only way to get a pitch's slots and calls `SlotGenerator` (never write another generator). Times go in 30-minute steps (`PitchScheduleRules.TimeStepMinutes`). The booking window is `Domain/Scheduling/BookingWindow` (today..today+30 in the club's time zone, today from `ClubTime.Today(timeProvider, …)`). Frontend: the `Horário` (Schedule) button on a pitch row (`PitchSection`) opens `ScheduleEditor` (RHF + Zod, seven rows, `type=time` in 30-minute steps, `Fechado` (Closed) checkbox; API keys `monday.closes` map to form paths `days.monday.closes` and a whole-day message to that day's toggle) and `SlotPreview` (date picker limited to `previewDateRange()`: Lisbon today..+30; times only through `formatLisbonSlotTime`). Date arithmetic on `YYYY-MM-DD` keys lives in `lib/datetime.ts` (`addDaysToDateKey`, `isDateKey`). Integration tests on a fake clock: `factory.WithWebHostBuilder(... ConfigureTestServices(... AddSingleton<TimeProvider>(new FakeTimeProvider(...))))`, but take sessions from the shared `factory`: access-token expiry is checked against the system clock.
- Blocks (US09, `BlockService`, controller `…/pitches/{pitchId}/blocks`): `Block` = pitch + UTC `[StartsAt, EndsAt)` + optional reason (≤ 200); input is Lisbon local `yyyy-MM-ddTHH:mm` (30-minute steps), converted with `ClubTime.ToUtc` (`BlockCheck`), start not in the past, end ≤ now + 90 days. Creating runs `IPitchLock.LockAsync(pitchId)` (Infrastructure `PitchLock`: transaction + `SELECT … FOR UPDATE` on the pitch row), then checks overlaps, saves and commits, all on the same `IAppDbContext`. Under the same lock, after the block check, confirmed bookings that overlap refuse the block (409 `block_overlaps_bookings`, ProblemDetails extension `bookings` with ids and UTC times); booking creation takes the same `IPitchLock` before checking blocks (docs/stack.md). Overlap is half-open, touching is fine; overlap = 409 `block_overlap`, deleting a started block = 422 `block_already_started` (`ErrorKind.Unprocessable`), unknown block = 404 `block_not_found`. The slot preview marks `blocked` slots (any overlap); free-slot logic for players (US17) must use the same overlap rule. Frontend: the `Bloqueios` (Blocks) button on a pitch row (`PitchSection`, one panel at a time with `Horário`) opens `BlocksSection` (list, removal with an inline confirmation, `BlockForm` with date + time fields per end; API `start`/`end` errors go on the date field of that end, `block_overlap` shows above the buttons) and the preview shows `Bloqueado` (Blocked). Block and preview queries live under `["pitches", clubId, pitchId, ...]`, so changing a block invalidates the preview.
- Bookings (T03, US18, `Application/Bookings/BookingService`, controller `api/bookings`, Player policy): `Booking` = pitch + **either** a player **or** a customer (US13: `player_id`, or `customer_name` + `customer_phone`; never both, never neither, `ck_bookings_player_or_customer`; `Booking.ForPlayer` / `Booking.ForCustomer`) + UTC `[StartsAt, EndsAt)` + price copied from the pitch + `Status` stored as the enum name (`HasConversion<string>()`), API codes `confirmed`/`cancelled_by_player`/`cancelled_by_club`/`no_show`. The request is `{ pitchId, startsAt }` with `startsAt` an instant with its zone; `Pitch.SlotStartingAt(startUtc, timeZone)` (generated slots of the start's Lisbon date) gives the end. Order: validation (400) → pitch (404) → owner active (`IAccountStore.IsActiveAsync`, 422 `club_unavailable`) → `IPitchLock` → re-read the pitch → inactive (422) → window on the Lisbon date (422 `outside_booking_window`) → slot match (422 `invalid_slot`) → started (422 `slot_started`) → blocks (409 `slot_blocked`) → insert through `IBookingStore.TryAddAsync`. Overlap with another booking is left to the exclusion constraint `bookings_no_overlap` (raw SQL in the `AddBookings` migration, needs `btree_gist`), whose 23P01 the store turns into 409 `slot_taken`; never add an app-level shortcut that bypasses it. `ServiceError.Extensions` carries extra ProblemDetails members (`count`, `bookings`). The owner slot preview also marks `booked` slots (confirmed bookings only). **My bookings and cancelling (US19):** `MyBookingsService` (`GET /api/me/bookings?scope=upcoming|past&page=`, `GET /api/bookings/{id}`, both Player-only and filtered by the session's player, so another player's booking is the same 404 `booking_not_found`) and `BookingCancellationService` (`POST /api/bookings/{id}/cancel`). The rules live in the entity: `Booking.CancelByPlayer(window, now)` returns a `CancellationOutcome` (`Cancelled`, `NotConfirmed`, `OutsideWindow`) and changes the status only for `Cancelled`; the deadline is `StartsAt - window`, cancelling needs `now` strictly before it, and the window is the club's **current** `CancellationWindowHours`, passed in, never stored in the booking. Order of refusals: 404 → 422 `booking_not_confirmed` → 422 `outside_cancellation_window` (extension `cancellationDeadline`, a UTC instant). Cancelling runs under `IPitchLock` and re-reads the booking inside it: that is what makes two concurrent cancels one 200 and one 422 (the test of 12 fails without the lock); bookings are never deleted, and the exclusion constraint only covers `Confirmed`, so a cancelled slot is free again. POST `/api/bookings` answers 201 with `Location: /api/bookings/{id}`. **Owner side (US11, US12; `Application/Bookings/ClubBookings.cs`, `ClubCalendar.cs`; controllers `ManageCalendarController`, `ManageBookingsController`):** `OwnedBookings.Of(clubId)` is the T02 way into bookings (through `OwnedPitches.Of`, so another owner's booking or a booking of the owner's other club is not there: 404 `club_not_found`, then 404 `booking_not_found`, both before the body or query is validated). `ClubCalendarService` answers `GET …/calendar?from=&to=&includeCancelled=` (local dates of the club, both included, ≤ 7 days, years 2000..2100; the range is `[ClubTime.ToUtc(from 00:00), ClubTime.ToUtc(to+1 00:00))`, so 25 October 2026 is 25 hours; a booking is in it if it overlaps; cancelled = `CancelledByPlayer`/`CancelledByClub`, a no-show is always shown; inactive pitches only if they have visible bookings; it does not use `PitchDayCalendar`, because it shows opening hours and what is there, not free slots). `ClubBookingService` has the details and `CancelAsync`: club → booking → validation (`reason` required, trimmed, ≤ 200) → `IPitchLock` → re-read → `Booking.CancelByClub(reason, now)` (`ClubCancellationOutcome`: 422 `booking_not_confirmed` before 422 `booking_already_started`; no window; starting now counts as started); it stores `CancellationReason` and `CancelledAt` (the player's cancel stores `CancelledAt` too). Player names are read only through `IAppDbContext.AccountNames` joined to bookings reached through an owned club: the only personal data an owner sees is the name (a test scans the bodies for the player's email and id; extend it when a field is added). Its cancellation email is queued in the same transaction (see Emails). **Customer bookings (US13):** `POST api/manage/clubs/{clubId}/bookings` (`ClubBookingService.CreateAsync`, body `{ pitchId, startsAt, customerName, customerPhone }`) is the owner's counterpart of US18 and uses the **same** `BookingSlotCheck` (inactive, window, grid, started, blocks) under the same `IPitchLock` and the same `IBookingStore.TryAddAsync` / `bookings_no_overlap` (409 `slot_taken`); never write a second copy of those rules. Order: club (404) → validation (400: name required ≤ 100, phone required, 9..15 digits, spaces removed) → pitch of this club (404) → owner active (422 `club_unavailable`) → lock → slot check → insert. 201 + relative `Location` to the owner's details. Name and phone are the US01 rules (`AccountNamePolicy`, `PhoneNumberPolicy`). A customer booking has no account, so the calendar and details **left-join** `AccountNames` (`bookerName` = customer name, `createdByClub` = true, `customerPhone` only in the details); player endpoints filter by `player_id` so these bookings are in no player's list and a player gets 404 for them. No email (the customer has no account). When a query is projected into a private row type and then filtered or ordered (`Where(row => row.Status…)`), build the row with an object initializer, not a constructor call: EF cannot translate member access through `new Row(…)`.
- Public catalog (US16, US17, `Application/Catalog`, controllers `ClubsController` and `LocalitiesController`, all `[AllowAnonymous]` and read-only): the counterpart of the owner rules. `VisibleClubs.All()` is the only way into clubs from the public pages (never read `IAppDbContext.Clubs` there): a club is visible when its owner is not deactivated (`IAppDbContext.ActiveAccountIds`, US29) and it has an active pitch; an unknown, empty or hidden club is the same 404 `club_not_found`, and a pitch that is unknown, inactive or from another club is 404 `pitch_not_found`, both checked before the date. Responses carry nothing about players or owners (no names, emails, account ids, booking or block ids, block reasons, or the club's own id) and a slot has one `available` flag, never a reason; every public endpoint has a test that scans its body for such data, so extend it when a field is added. Endpoints: `GET /api/clubs?sport=&locality=&date=&page=` (20 per page, ordered by name ignoring case, `hasFreeSlots` worked out only for the page's clubs), `GET /api/localities`, `GET /api/clubs/{slug}`, `GET /api/clubs/{slug}/pitches/{pitchId}/slots?date=`. Locality search = equality on `clubs.locality_key` (`ClubRules.LocalityKey`: no accents, lower case, single spaces; kept in step by `Club`, indexed). **One slot calculation:** `PitchDayCalendar` turns generated slots into `DaySlot`s (blocked/booked, reading blocks and confirmed bookings of many pitches with one query each) and `DaySlot.IsFreeAt(now)` is the only definition of "free" (nothing overlaps, even partly, and it has not started; starting now counts as started via `TimeSlot.HasStartedBy`); the owner preview, the player's slots and the search all use them, so never write another. `BookingDateInput.Parse` gives all three the same date checks (today..today+30 in Lisbon, `yyyy-MM-dd`, 400 on `date`). Query-string numbers that a client can get wrong are read as text and judged by our own validation, so the error is pt-PT and not MVC's English binding message (see the search's `page`).
- Emails (US22, `Application/Notifications`, `Infrastructure/Notifications`): an **outbox**. `BookingEmailOutbox` adds an `OutboxMessage` (type + JSON `BookingEmailPayload`: player id and what the email shows, never the address) to the same `IAppDbContext` **before** the caller's `SaveChangesAsync`, inside its pitch-lock transaction: `BookingService` (confirmation, before `IBookingStore.TryAddAsync`, which on 23P01 detaches every Added entry so the email goes with the booking), `BookingCancellationService` and `ClubBookingService.CancelAsync`. A booking without a player (US13) queues nothing. `OutboxDispatcher` (`BackgroundService`, scope per pass, `Outbox:Enabled`, waits on the injected `TimeProvider`) runs `OutboxProcessor.ProcessDueAsync`: `SELECT … FOR UPDATE SKIP LOCKED` in a transaction held for the batch, recipient (current email and name) read from `users` at send time, `BookingEmailComposer` (pt-PT, club time zone, `(verão)` ("summer")/`(inverno)` ("winter"), `18,50 €`, text + HTML with a minimal escape), `IEmailSender` (`SmtpEmailSender`, MailKit, connection per message). Failures: `OutboxMessage.RecordFailure` with `OutboxRetry` (doubling back-off), `last_error` = exception **type** only; given up → Warning with id and type, never the address. At least once. Settings `Email` and `Outbox` with validators and `ValidateOnStart`; placeholders in Program's OpenAPI block. Tests: the shared `ApiFactory` sets `Outbox:Enabled=false` and dummy `Email` settings; worker tests use `CreateIsolatedApp` (own database, so no other test's messages) with `FakeEmailSender` and a fake clock and call the processor themselves; `MailpitTests` runs a real Mailpit container.
- Demo data (T05, `Infrastructure/Demo`): `dotnet run --project backend/src/SportsBooking.Api -- seed-demo` (`docker compose run --rm api seed-demo`). `Program.cs` runs `DemoDataCommand` only when the command line is exactly `seed-demo`, after migrations and the admin seed, and exits without starting the host (no `BackgroundService`, so no email). `DemoDataSeeder` refuses in Production unless `DemoData:AllowInProduction` is true (env `DemoData__AllowInProduction`, only on that process, T06) and when any Owner or Player exists, and does everything in one transaction through the entities (`Club.Create`, `Pitch.ChangeSchedule`, `Booking.ForPlayer`/`ForCustomer`, `CancelByPlayer`, `CancelByClub`, `MarkNoShow`); it builds bookings itself, which is the only thing that bypasses the service's "not in the past" rule. Deterministic: `Random(20260101)` and a "now" fixed at the start of today in Lisbon (the same day gives the same data, ids and password hashes aside); one hash is made and shared by all accounts (`DemoPassword`, development only, in the README); addresses are on `example.test`; the outbox is never touched. The catalogue (clubs, pitches, blocks, names) is in `DemoCatalog.cs`. `AppUser.RegisteredAt` (`users.registered_at`) is set by registration and the seed; tests that make an `AppUser` pass a date. `DemoDataTests` seeds on isolated databases; the tests that sign in use a seed on a clock that starts at the real time, because an access token is checked against the system clock.
- Admin numbers (US24, US25, US26, `Application/Admin`, controller `AdminController`, `api/admin`, `[Authorize(Policy = Profiles.Admin)]`): counts only, never a player's name, email, phone or id. Accounts are read through `IAppDbContext.AccountProfiles` (profile, registration date, deactivated: **no personal field, keep it that way**) and, for the owners' list only, `OwnerAccounts` (name and email of owners; players are never in it); every endpoint of the area has a test that scans bodies for a seeded player's name, email and id, and `AdminAreaAccessTests` discovers every `/api/admin` route and checks 401/403. Everything is aggregated by the database (`GROUP BY`, correlated `COUNT`, `COUNT(DISTINCT)` that must skip the `NULL` player of a customer booking). Bookings over time (`IBookingStatistics`, Infrastructure `BookingStatistics`, raw SQL `date_trunc(unit, created_at AT TIME ZONE 'Europe/Lisbon')`) counts by **creation** time on the Lisbon date; `ReportingPeriods` is the one place for period starts (Monday weeks, months), range widening to whole periods, and maximums (366 days, 104 weeks, 60 months); empty periods are filled in by the service. Admin integration tests use `AdminTestApp` (own database, fixed clock 2026-10-28, admin session from the shared factory, few hosts at once because each has a connection pool). - State: **TanStack Query** for anything from the API (invalidate after mutations, refetch slots on 409). There is **no Zustand**: what the user chooses (the booking step `?pitch=&date=&slot=&weeks=`, the calendar view, search filters, pages) lives in the page address, read with `useSearchParams` and written with `router.replace`, so a visitor sent to sign in comes back to the same choice and links are shareable (docs/stack.md, "Estado"). Never copy API data into other state, and never put tokens or personal data in `localStorage`.
- Forms: React Hook Form + Zod (UX only; the API always re-validates with FluentValidation). Map API `errors` to fields with `setError`. Zod schemas mirror the API's limits and pt-PT messages (e.g. `features/auth/schemas/register.ts`). Use `noValidate` so browser validation does not replace ours. Messages by code through `useApiErrors()` (`src/lib/api/error-messages.ts`, catalog namespace `apiErrors`; an unknown code gets `unknown_error`'s text); field errors of a 400 through `showApiFieldErrors(…, useApiFieldMessage(scope))`, which shows the catalog's words for the field (`fieldErrors.*`), never the API's text; unexpected mutation errors go to a toast (sonner). Current user: `useCurrentUser()` (`features/auth`), query key `["auth", "me"]`.
- Integration tests run against real PostgreSQL (Testcontainers), never the EF in-memory provider.
- End-to-end (T08, `e2e/`, own `package.json`): five Playwright tests (Chromium; the browser asks for `pt-PT`, the fifth switches to English, T09) against the `docker compose` stack with the demo data, in `.github/workflows/e2e.yml` (separate from `ci.yml`, so `deploy.yml` does not wait for it). Role/name locators, no fixed sleeps, one worker, tests clean up the bookings they make and use days 20+ ahead of the seeded ones. Anything else in a UI story is still checked by hand in the browser (docs/stack.md, "Testes").

## Business rules (decided)
- One email = one account = one profile.
- An owner may have several clubs; a club has exactly one owner.
- Cancellation window per club, default 24 h; the window in force at cancellation time applies.
- Bookings from today up to 30 days ahead. Slot length per pitch: 30, 60 or 90 min.
- Bookings are never deleted; they change status: Confirmed, CancelledByPlayer, CancelledByClub, NoShow (UI shows pt-PT labels).
- Each booking stores the price at booking time. No payments in the MVP.
- Dates stored in UTC, shown in Lisbon time regardless of the browser time zone.
- One marketplace: a player account works at every club of every owner; no per-owner sites or domains. URLs: public club page `/clubs/{slug}` (unique slug from the name at creation, unchanged on rename); owner area `/manage/clubs/{id}` (public GUID).
- Another owner's resources return 404 (don't reveal existence); wrong profile returns 403.

## Gotchas
- Next.js 16.4 differs from older versions (e.g. `error.tsx` gets `retry`, `cacheComponents` is on, `proxy.ts` replaces `middleware.ts`). Read [frontend/AGENTS.md](frontend/AGENTS.md) and the bundled docs in `frontend/node_modules/next/dist/docs/` before writing frontend code.
- Build-time OpenAPI generation starts the app as `GetDocument.Insider`; `Program.cs` gives it placeholder settings and skips migrations. Keep startup code safe for that.
- Integration tests: the shared `ApiFactory` host applies migrations on startup (`Database:ApplyMigrationsOnStartup=true`, as Development does). For startup behaviour (seeding), use `factory.CreateIsolatedApp(databaseName, settings)`: own database, captured logs via `GetFakeLogCollector()`.
- Integration test data: `TestVenues` (extension methods on the app factory) builds owners, clubs, pitches (with opening hours), blocks, bookings, price and schedule changes and deactivations straight through the domain model, with unique names and slugs; use it instead of going through the owner API when a test only needs data to read back. The whole assembly shares one database, so give each test its own locality or club names when it lists things. For a fixed clock and captured logs: `factory.WithWebHostBuilder(b => { b.ConfigureTestServices(s => s.AddSingleton<TimeProvider>(new FakeTimeProvider(...))); b.ConfigureLogging(l => l.AddFakeLogging()); })`; starting the host runs its own database commands, so read `app.Services` before taking a "before" count. The whole suite needs Docker running (Testcontainers): without it every integration test fails to connect, which looks like hundreds of failures.
- Integration test clients: the site origin is `https://localhost` (`ApiFactory.SiteOrigin`; HTTPS so Secure cookies work). `factory.CreateBrowserClient()` = cookie jar + `Origin`; `factory.CreateSiteClient()` = `Origin`, no jar (send cookies with `request.WithCookies(...)`, read them with `response.SetCookies()`); `factory.CreateSignedInPlayerAsync()` / `CreateSignedInAsync(profile)` give an account and session tokens without slow password hashing; `CreateAccountAsync(profile, password)` makes an account of any profile that can log in.
- The test host (and only it) adds `TestClientAddress` (header `X-Test-Connection-Address` sets the connection IP; `request.From("203.0.113.10")`) and `ProfileAreasTestController` (`/test-only/areas/{player|owner|admin}`). It sets very high rate limits because every test request shares one address; rate limiting is tested on isolated apps (`RateLimitingTests`).
- Build-time OpenAPI generation also runs `ValidateOnStart`: every new required setting needs a placeholder in the `isOpenApiGeneration` block of `Program.cs`.
- Frontend component tests: MSW (`src/test/msw.ts`) is global and fails on unhandled requests; add handlers with `server.use(...)`. Render with `renderWithProviders` (`src/test/render.tsx`) and mock `next/navigation` where a component uses the router. For components driven by the URL (`useSearchParams`, `router.replace`), mock `next/navigation` with `vi.mock("next/navigation", async () => import("@/test/navigation"))`: its URL is real (`resetNavigation("/path?query")`, `currentPath()`), so a `router.replace` re-renders the component as in the app; it also exports a `notFound` that throws `NotFoundSignal`.
- CI: the backend job installs the .NET SDK with the official `dotnet-install.sh` (exact version from `global.json`, from builds.dotnet.microsoft.com) instead of `actions/setup-dotnet`, because setup-dotnet's downloads go through aka.ms to `dotnetorigin.blob.core.windows.net`, which answers 409 ([actions/setup-dotnet#794](https://github.com/actions/setup-dotnet/issues/794)). It can go back to `setup-dotnet` once that issue is fixed (check that its install log no longer mentions `dotnetorigin`).
- `dotnet ef migrations remove` needs a running database; to drop an unapplied migration, delete its two files and restore `AppDbContextModelSnapshot.cs` from git.
- EF migrations folder is marked `generated_code` (its own `.editorconfig`); test projects allow underscores in test names (CA1707 off).

## Definition of done
A story is done only when every acceptance criterion is covered by tests (unit, integration and/or component) and the CI is green.
